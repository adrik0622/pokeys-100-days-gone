## V2 companion server-adapter regression harness — source/mocked boundary

Added `tests/lua/v2_server_spec.lua`, which executes the actual companion `V2Server`/`V2Rules` adapter with mocked game callbacks and mocked The Mission history, Jeem APIs, player inventory and item synchronization. It verifies that forged completion/account/reward arguments, wrong-module messages and unsupported completion commands cannot cause credit; the native mission definition/location gate is installed; completion credit is deferred until Jeem is available and applied once per server account across an `OnInitGlobalModData` reopen; and successful aid is one fixed item regardless of client-supplied item/count/account fields, followed by a shared cooldown that also refuses a second completed account.

Two partial-effect cases are injected. First, Jeem standing is changed, then relay recovery repair throws: the bridge marks the account grant `incident` and a repeated check after a mocked data-init reopen does not add a second standing delta. Second, an aid item is added server-side, then `sendAddItemToContainer` throws: the bridge leaves `aidPending` latched, leaves the previous cooldown timestamp untouched, and refuses another item after a mocked data-init reopen. These are deliberate fail-closed behaviors because replaying could duplicate reputation or an item when the first effect's delivery is ambiguous. There is no in-game reconciliation command. **Human review HR-010** tracks whether to keep manual inspection as the only remedy or add a constrained operator repair flow.

This harness passed under Lua 5.1 and is included in `pytest`. Its two-account check is sequential shared-state behavior, not a simultaneous two-client race. The follow-up harness also re-enters the completion path while a grant is pending and injects a second account's aid request during the first account's in-flight item addition; pending reservations prevent duplicate credit/item in these mocked callback paths. This is ordering/re-entrancy evidence, **not** simultaneous network-client or engine-thread evidence. The harness also does not certify The Mission/Jeem engine integration, persistent GlobalModData serialization, hard-crash atomicity or actual container-sync behavior. The next safe runtime step is a dedicated failure-boundary test in a fresh disposable profile if a reliable engine injection seam can be established; otherwise keep the production latch unchanged and do not simulate recovery by clearing saved state.

### Persistent-state validation hardening — source/mocked

Follow-up reliability work validates schema-1 records before the bridge accepts them: revision and world-hour fields must be finite/nonnegative, revisions integral, grant account keys bounded, grant status/time/delta consistent (an applied grant must contain its recorded delta), and a pending aid latch must contain a bounded operator name and valid timestamp. Jeem's computed rate is checked before standing mutation; malformed usernames are ignored before touching the transient rate table. Malformed/unsupported state still disables only this opt-in bridge and is left unchanged for inspection.

Lua 5.1 regression cases cover missing/overlong account data, invalid timestamps/revision, inconsistent applied grants, invalid pending aid records, non-finite Jeem rates and a missing username. Full Python suite: **68 tests pass**; manifest and Lua syntax checks pass. This is mocked/source-boundary evidence; it does not establish engine GlobalModData serialization, crash atomicity, or simultaneous client processing.
